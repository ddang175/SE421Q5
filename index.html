EXPERIMENT 01 / AVAILABILITY

Make a small table do more work.

Algorithmic complexity

Think of eight labeled drawers. A rule sends each key to a drawer, called a bucket. Before adding a key, the table checks the keys already there for a duplicate. Different keys sent to the same bucket collide: bucket = key % 8. You control the keys; the consequence is extra work.

Where the extra work comes from

for each key:
  bucket = key % 8
  for each existing key in bucket:
    compare(existing, key)
  append key to bucket

All-collision insertion costs 0 + 1 + … + (n−1) = n(n−1)/2, or O(n²). With just eight fixed buckets, even spread input eventually grows quadratically, but with a smaller coefficient. Expected O(n) total insertion requires keeping the load factor bounded as the table grows.

What would help in a real system?

Use a hash strategy designed for adversarial input, grow the table as needed, bound request sizes, and consider structures that bound collision cost. Resizing alone does not guarantee safety against keys chosen to collide. The modulo hash here is deliberately weak; it is a teaching model, not a claim about every hash table.

What this model does and does not prove
Mismatch counting checks all four digits, yet leaks their agreement through its output. In early-exit mode, a longer correct prefix can cause more work. A full match and a last-digit mismatch both take four comparisons.
The fixed-work model compares every digit and exposes no mismatch count. For equal-length guesses, its work signal is flat. Real timing also depends on compilers, hardware, and noise. JavaScript operation counts do not establish constant-time security; use vetted comparison primitives in real authentication systems.

    Why does the ending matter?
    a+ means one or more a's. In (a+)+, the outside + repeats those groups. The same four letters can be [aaaa], [aaa][a], or several other groupings. The anchors ^ and $ require the whole input to fit.
    Without !, the first complete grouping succeeds. With !, regrouping cannot remove the bad ending. A backtracking matcher may keep searching before it rejects the input.
    Try four letters, then five, with ! checked. The possible complete groupings double, from 8 to 16. Each gap between letters can either split a group or join it: 2^(n−1) choices.
    Change the rule, keep the meaning
    Switch to ^a+$. For these inputs it accepts the same text, but a direct scan can inspect each character once, with no alternative groupings. The display counts one candidate and reports character inspections separately.
    This is an illustrative enumeration of complete groupings, not a regex engine's exact execution order, all partial paths, elapsed time, or a measured slowdown ratio. Engines and optimizations vary. The email pattern in question three is different; this small example isolates ambiguous repetition.
    In real systems, review ambiguous patterns, use suitable matching engines, and limit input and execution resources. Read OWASP's ReDoS explanation ↗
    
  
    
  
    THE CONNECTION
    Chosen input → changed behavior → security consequence.
    Collisions and repeated matching attempts increase work and threaten availability. Secret-dependent output or work can reveal information and threaten confidentiality. Ask both: “How much work can this input cause?” and “What can someone learn from the response?”
